## LC70：先不要说 DP，先把楼梯走法数出来

有 `n` 阶楼梯，每次可以走 1 阶或 2 阶。问：走到第 `n` 阶一共有多少种不同走法？

例如到第 3 阶有三种：

```text
1 + 1 + 1
1 + 2
2 + 1
```

重点是走法的顺序不同就算不同。`1 + 2` 和 `2 + 1` 是两种走法。

先从非常小的 n 开始，不看任何公式：

| 目标阶数 | 走法 | 总数 |
|---:|---|---:|
| 0 | 什么也不走 | 1 |
| 1 | `1` | 1 |
| 2 | `1 + 1`、`2` | 2 |
| 3 | `1 + 1 + 1`、`1 + 2`、`2 + 1` | 3 |

为什么第 0 阶算 1 种？它表示“已经站在起点，什么都不做”这一种完整方案。这个定义不是凑数，它会让后面的转移规律在边界处也成立。

## 只盯住最后一步：到第 4 阶之前，你来自哪里？

想要到第 4 阶，最后一次只能走 1 阶或 2 阶，没有第三种可能：

```text
最后走 1 阶：你在第 3 阶，然后再走 1 阶到第 4 阶。
最后走 2 阶：你在第 2 阶，然后再走 2 阶到第 4 阶。
```

到第 3 阶的每一种走法，最后补一个 1，都会变成一种到第 4 阶的走法。

```text
到 3 阶的走法：
1+1+1  ->  1+1+1+1
1+2    ->  1+2+1
2+1    ->  2+1+1
```

因此“最后走 1 阶”的走法数量，恰好等于到第 3 阶的走法数量，也就是 3。

同理，到第 2 阶的两种走法后面补一个 2：

```text
1+1  ->  1+1+2
2    ->  2+2
```

因此“最后走 2 阶”的走法数量是 2。

这两组走法不会重复：一组最后一步是 1，另一组最后一步是 2。它们也没有遗漏：到第 4 阶的最后一步只能是 1 或 2。

所以：

```text
到第 4 阶的总走法
= 最后走 1 阶的走法 + 最后走 2 阶的走法
= 到第 3 阶的走法数 + 到第 2 阶的走法数
= 3 + 2
= 5
```

## 先得到规律，再给它取名字

把“到第 i 阶的走法数”记作 `ways[i]`。刚才的最后一步推理适用于任意 `i >= 2`：

```text
ways[i] = ways[i - 1] + ways[i - 2]
```

这里每个部分都有明确含义：

| 表达式 | 人话含义 |
|---|---|
| `ways[i]` | 走到第 i 阶的总走法数 |
| `ways[i - 1]` | 最后走 1 阶前，已经到第 i - 1 阶的所有走法 |
| `ways[i - 2]` | 最后走 2 阶前，已经到第 i - 2 阶的所有走法 |

这才是动态规划的起点：

> 先把一个问题的答案定义成状态，再从最后一个选择推导这个状态依赖哪些更小状态。

不是先背 `dp[i] = dp[i - 1] + dp[i - 2]`。

## 把所有小答案填成一张表

从已知的起点开始：

```text
ways[0] = 1
ways[1] = 1
```

接下来从小到大填表：

| i | 计算 | `ways[i]` |
|---:|---|---:|
| 0 | 起点：什么也不走 | 1 |
| 1 | 只有 `1` | 1 |
| 2 | `ways[1] + ways[0] = 1 + 1` | 2 |
| 3 | `ways[2] + ways[1] = 2 + 1` | 3 |
| 4 | `ways[3] + ways[2] = 3 + 2` | 5 |
| 5 | `ways[4] + ways[3] = 5 + 3` | 8 |

表格从左向右填，是因为 `ways[5]` 需要已知的 `ways[4]` 和 `ways[3]`。这就是**遍历顺序**的原因，不是习惯写法。

## 为什么不直接写递归？先看重复计算

最自然的递归会写成：

```text
count(5) = count(4) + count(3)
count(4) = count(3) + count(2)
```

你会发现 `count(3)` 被算了两次：一次来自 `count(5)`，一次来自 `count(4)`。n 更大时，这种重复会越来越多。

动态规划做的事很简单：

```text
第一次算出 ways[3] 后，把 3 保存下来。
以后需要 ways[3] 时，直接读取，不再重新展开它。
```

所以 DP 不是神秘的另一种算法；它是：

> 把会被重复求解的小问题答案保存下来，按依赖顺序复用。

## 到这里才看代码：数组就是刚才的表格

下面的数组 `ways` 与上一节表格一一对应：

```text
ways[0] = 1
ways[1] = 1
for 循环从 2 开始，依次填 ways[2]、ways[3] ... ways[n]
```

第一次阅读代码时，只看循环中的这一行：

```js
ways[step] = ways[step - 1] + ways[step - 2];
```

它就是“最后一步走 1 阶或 2 阶”的翻译。

## 可直接运行的代码

```js
/**
 * 返回每次走 1 阶或 2 阶时，到达 stepCount 阶的不同走法数量。
 *
 * @param {number} stepCount
 * @returns {number}
 */
function climbStairs(stepCount) {
  if (!Number.isInteger(stepCount) || stepCount < 0) {
    return 0;
  }

  const ways = new Array(stepCount + 1).fill(0);
  ways[0] = 1;

  if (stepCount === 0) {
    return ways[0];
  }

  ways[1] = 1;

  for (let step = 2; step <= stepCount; step += 1) {
    // 最后一步要么从 step - 1 走 1 阶，要么从 step - 2 走 2 阶。
    ways[step] = ways[step - 1] + ways[step - 2];
  }

  return ways[stepCount];
}

console.log(climbStairs(0)); // 1
console.log(climbStairs(1)); // 1
console.log(climbStairs(2)); // 2
console.log(climbStairs(3)); // 3
console.log(climbStairs(5)); // 8
console.log(climbStairs(-1)); // 0
```

## 代码逐段对应手工表

| 代码 | 对应的手工含义 |
|---|---|
| `new Array(stepCount + 1)` | 准备从第 0 阶存到第 n 阶，共需要 n + 1 个位置 |
| `ways[0] = 1` | 起点处“什么也不走”有 1 种方案 |
| `ways[1] = 1` | 走到第 1 阶只有 `1` 这一种方案 |
| `step = 2` 开始循环 | 从第 2 阶开始，答案才需要前两个状态推导 |
| `ways[step - 1] + ways[step - 2]` | 按最后一步分成走 1 阶与走 2 阶两组 |

## 复杂度：从数组长度和循环次数开始数

设输入规模为：

```text
n = stepCount
```

### 时间复杂度

数组需要创建 `n + 1` 个位置；循环从 2 到 n：

```text
step = 2、3、4 ... n
```

循环次数是 `n - 1` 次。每次只做一次加法、两次读取、一次写入，都是常数工作：

```text
(n - 1) 次 * 常数工作 = O(n)
```

初始化数组也是 `O(n)`，二者是先后执行：

```text
O(n) + O(n) = O(n)
```

### 空间复杂度

`ways` 从下标 0 保存到下标 n，一共 `n + 1` 个数：

```text
空间 = O(n)
```

本题最终只需要 `ways[n]`，每次计算新值只依赖前两个值。因此之后可以把数组压缩成两个变量，把辅助空间降为 `O(1)`。但先用数组把“状态表”写清楚，不要一开始为了省空间把状态含义藏掉。
